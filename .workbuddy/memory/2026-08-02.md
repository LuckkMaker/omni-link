# 2026-08-02

## monitor 波形采样率优化调研（对比 plink）

- 核实了 https://github.com/pushk3n/plink（pyOCD 直连 DAP 读内存画波形，PyQt6+pyqtgraph）
- **4500Hz 说法属实**：commit e2d43cd "针对 dap-link V2 bulk升级, 10MHz仅采样模式下达到4500+Hz"，条件是 10MHz SWD + DAPLink V2 bulk + "仅采样"（关闭绘图跑纯采样循环，非 UI 模式开关）
- plink 核心优化手段：
  1. SWD 时钟默认 8MHz（omni 当前 1MHz，差 8-10 倍，是最大瓶颈）
  2. 跨 Block 流水线读取 `_pipelined_batch_read()`：直接操作 AP/DP（dp.write_ap + read_ap_multiple + now=False + dp.flush()），多 Block 命令一次发出，Bulk V2 pipeline_depth=6+
  3. Block 合并激进：merge_gap=65536（64KB），max_bytes: HID 1024B / Bulk 2048B，最小载荷比 20%
  4. 读取计划缓存 `_get_read_plan()`（omni 已有 vars_cache 缓存分组）
  5. `enable_read_cache=False` 保证实时性
  6. busy-wait 高精度节流 `_busy_wait_until`（omni 用 time.sleep，精度差）
  7. 热路径零内存分配：预编译 struct.Struct + numpy ring buffer
  8. 数据全进程内，无 WS/JSON 序列化（omni 有 WS+JSON 开销）
- omni 现有差距（文件级）：
  - pyocd_backend.py:176 `actual_speed = speed if speed else 1000000`（1MHz）
  - monitor_backend.py:41 `MERGE_GAP = 16`（plink 64KB）
  - monitor_backend.py `_read_variables` 逐 group 串行 read_memory_block32，无跨 block 流水线
  - monitor_backend.py:489 `PUSH_BATCH = 8` 固定，WS 消息数 = rate/8
  - monitor.store.ts:212 zustand `[...s.samples, ...pts]` 全量拷贝
- 建议优化优先级：① SWD 时钟提到 4-8MHz 并暴露前端 speed ② 借鉴流水线批量读（AP/DP 层）③ MERGE_GAP 放大+载荷比保护 ④ PUSH_BATCH 动态化/负载减重 ⑤ busy-wait 节流

## 影响面评估（用户问是否影响其他页面）

- **连接全局共享**：所有功能（monitor/flash/commander/RTT/SWV）共用同一 pyOCD session（`backend._get_session(uid)`），SWD 时钟改动是全局的，无法只对 monitor 提频
- **前端 speed 链路已通**：probe.store.ts:103 `pendingSpeed: 1_000_000`（默认 1MHz），probe.service.ts 已传 options.speed，只是 UI 未暴露控件 → P0 只需加 UI 控件+调整默认值，后端 0 改动

- **影响结论**：P0 全局影响（性能提升为主，风险=高时钟下探针/线缆稳定性，缓解=保留默认+可配置+失败降频重试，pyocd 有 fail_safe）；P1/P2/P3 全封闭在 monitor 私有实现（_read_variables/_build_read_groups/_emit_samples），保持公开方法签名不变即不影响其他页面；P2 若改 payload 结构需前后端契约同步（只影响 monitor 生态）；流水线读必须带 fallback 回退 read_memory_block32（plink 同款做法）

## 流水线失败根因修复（用户贴日志确认）

- **日志证据**：`WARNING: Monitor pipelined read failed ... 'Apm32f407ig' object has no attribute 'ap'`（3 条 = 3 次采样启动，降级机制正常）
- **根因**：项目自带 APM32F407IG target（python/pyocd/target/builtin/geehy/target_APM32F407xx.py）继承 **CoreSightTarget 而非 CortexM**，没有 `.ap` 属性（CortexM 的 `.ap` 来自构造参数 CoreSightCoreComponent.__init__）；CoreSightTarget 暴露的是 `.dp` + `.aps` + **`.first_ap`**（coresight_target.py:354-358，排序后第一个 AP，单核=AHB-AP#0）
- **修复**：`_pipelined_read` 里 `ap = getattr(target,'ap',None) or getattr(target,'first_ap',None)`，两者皆无才抛 AttributeError → 触发降级
- 测试用例10（模拟无 .ap 有 .first_ap 的 target）全 PASS
- 结论：修复后 bulk 探针（DAPLink V2/WinUSB）流水线才真正启用；HID 探针按设计走串行（plink 同判据），性能也不低于改动前（串行同样吃到 64KB 合并+对齐）
- **用户澄清 + 机制确认**：项目实际未用内置 target_APM32F407xx.py，target 从 DFP 动态导入。pyocd 机制（pack_target.py:535）：`type(subclassName, (superklass,), {__init__: _pack_target__init__})`，无 family 匹配时 superklass=CoreSightTarget，`_pack_target__init__`（433）调 `super().__init__` → CoreSightTarget.__init__ → **有 .dp/.aps/.first_ap，无 .ap**（与报错吻合）。`.first_ap` 是 CoreSightTarget property（coresight_target.py:354），pyocd 内部 pack_target.py:302 也用 `self._target.first_ap` → 上一轮的 ap→first_ap 回退修复对 DFP target 同样有效，无需再改
- **用户新日志确认修复生效**：08:19:45 启动，无 "pipelined read failed" warning

## 采样率实测数据与节流优化（用户测试固件 dsp_wave）

- **用户实测**：设定 1kHz → actual_rate_hz ≈ 500+；设定 5kHz → ≈ 1kHz
- **解读**：① ~1kHz 是读取硬上限（单帧 SWD 读取 ~1ms，5kHz 也到不了更高）② 1kHz 设定只剩 500 是因为 **Windows 上 time.sleep 最小精度 ~1ms**，`sleep(interval-elapsed)` 每帧多撑 ~1ms
- **已改**（monitor_backend.py `_sample_loop` 节流）：混合节流 = sleep_time>2ms 先 `time.sleep(sleep_time-0.001)` 再忙等 `while monotonic()-t0 < interval: pass`（monotonic 与 t0 同源，不能用 perf_counter 混算）；消除 sleep 精度损耗
- **已改**：start() 启动日志加 `probe_transport=bulk/hid`，便于确认流水线是否启用（bulk 才走流水线）
- **待验证**：节流优化后 1kHz 设定应回升到接近 ~1kHz 硬上限；要突破 1kHz 需降低读取耗时 → P0（连接页提高 SWD 时钟，用户已有速度选项）或确认探针为 bulk（流水线生效）

## 修复：ELF 数组变量不显示元素选择（用真实固件 omni.axf 定位）
