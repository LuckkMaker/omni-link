# OMNI Tool Bootloader 固件改动清单

> 状态：**待评审**（本文档为上位机侧提出的需求，供固件侧评估与实现）
> 关联上位机：`/omni-tool` 页（M1 已完成，见 `omni-tool-plan.md`）
> 目标固件：`omni-emb/applications/industrial/omni_tool_boot`
> 关联应用：`omni_tool_app`

---

## 1. 背景与结论

当前 boot 的 4 个功能码（FC101 下载 / FC102 上传 / FC103 控制 / FC104 信息）**协议层已经完整**，上位机侧无需固件改动即可完成自升级闭环。

但从**产品化**角度看，现有 boot 存在三个缺口，核心是：**"镜像是否有效"的判断权完全在上位机手里，boot 自己什么都不管**。

| # | 缺口 | 风险 | 是否阻断发货 |
|---|---|---|---|
| G1 | 无固件完整性自校验 | 上位机不在场时坏镜像照样跳转 → 变砖 | **是** |
| G2 | boot 区可被擦写 | 参数传错/恶意帧擦掉 boot 自身 → 永久变砖 | **是** |
| G3 | 擦写中掉电无保护 | 掉电后 boot 分不清"空"和"半截坏镜像" | **是** |

**这三条都是"boot 侧单方面就能完成"的加固，不需要上位机配合，属于 bootloader 的基本职责。**

## 2. 现状确认（已核对）

### 2.1 Flash 分区（STM32F407IG，1MB）

| 区段 | 起止 | 大小 | 说明 |
|---|---|---|---|
| Boot | `0x08000000` ~ `0x0800FFFF` | 64 KB | bootloader |
| App | `0x08010000` ~ `0x080DFFFF` | 832 KB | 目标固件 |
| DAP / 保留 | `0x080E0000` ~ `0x080FFFFF` | 128 KB | CMSIS-DAP |

扇区布局（**boot 一次只能擦一个扇区**，单扇区 1~2s）：

| 扇区 | 起始 | 大小 |
|---|---|---|
| 6 | `0x08010000` | 64 KB |
| 7~12 | `0x08020000` / `0x08040000` / `0x08060000` / `0x08080000` / `0x080A0000` / `0x080C0000` | 各 128 KB |

### 2.2 现有协议

| FC | 语义 | 现状评价 |
|---|---|---|
| FC101 `0x65` | 下载 | ✅ 可用 |
| FC102 `0x66` | 上传 | ✅ 可用 |
| FC103 `0x67` | 控制（`0x01` SET_ADDR / `0x02` ERASE / `0x03` LEAVE） | ⚠️ **缺范围保护**（G2） |
| FC104 `0x68` | 读信息（版本 + MCU UID） | ⚠️ 无协议版本字段（G4） |

## 3. 改动项

### G1 — 固件完整性自校验【P0】

#### 问题

上位机的"校验"是 **回读后逐字节比对**（[python/omni_tools/session.py](../python/omni_tools/session.py)），属于**外部验证**。存在两个盲区：

1. 用串口工具等第三方工具裸刷时，boot 不会做任何检查，`FC103 LEAVE` 直接跳转。
2. 逐字节比对只能证明"和上位机手里那份一致"，无法证明"这是一份能启动的固件"。

#### 方案

在镜像尾部追加 **CRC32 + 长度尾块**，boot 在 `LEAVE` 前自行校验。

##### 尾块格式（放在镜像末尾，紧跟固件最后一个字节）

| 偏移 | 长度 | 内容 | 说明 |
|---|---|---|---|
| +0 | 4 B | `IMAGE_LEN` | **App 区实际长度**（字节数，不含尾块自身） |
| +4 | 4 B | `IMAGE_CRC32` | 对 `IMAGE_LEN` 字节内容的 CRC32 |
| +8 | 4 B | `MAGIC` | `0x4F54494D`（ASCII `"OTIM"`），用于快速判别尾块存在性 |
| | **12 B** | | 尾块总长 |

**CRC32 算法**：标准 IEEE 802.3 多项式 `0x04C11DB7`（**反射实现**，init `0xFFFFFFFF`，final XOR `0xFFFFFFFF`）—— 即 zlib/Python `binascii.crc32` / STM32 官方 `CRC_Calc` HAL 同款。
**上位机侧已用 Python `zlib.crc32` 交叉验证过实现口径。**

##### boot 侧逻辑

```
FC103 LEAVE:
    1. 读 IMAGE_LEN / IMAGE_CRC32 / MAGIC（地址 = SET_ADDR 时记录的地址 + IMAGE_LEN）
    2. 若 MAGIC != 0x4F54494D        → 拒绝，返回异常码（镜像无尾块）
    3. 若 IMAGE_LEN 越界或为 0        → 拒绝，返回异常码
    4. 分块读回 IMAGE_LEN 字节，边读边算 CRC32
    5. 若 CRC32 != IMAGE_CRC32        → 拒绝，返回异常码（并保留在 boot，不跳转）
    6. 全部通过 → 正常跳转
```

##### 兼容性（**重要**）

**必须向后兼容**，否则旧固件无法再用 boot 升级：

- 定义 `SET_ADDR` 响应中回显一个**镜像格式版本位**（见 G4）
- 格式版本为 `LEGACY` 时，跳过 CRC 校验，走现有行为
- 格式版本为 `CRC32_V1` 时，启用上述校验

否则一旦上线 CRC 校验，所有**存量设备上的存量 app** 都将无法被升级 —— 那是灾难性的。

##### 异常码建议

| 码 | 含义 |
|---|---|
| `0x10` | 镜像尾块 MAGIC 不匹配 |
| `0x11` | 镜像长度非法 |
| `0x12` | CRC32 校验失败 |

### G2 — 保护 Boot 区自身【P0】

#### 问题

`FC103 ERASE` / `FC101 DOWNLOAD` 目前**不校验地址范围**。上位机侧虽有范围检查（[python/omni_tools/session.py](../python/omni_tools/session.py) 的 `_validate_range`），但：

- 那只是**上位机的自律**，不构成防护
- 绕过上位机直接发 Modbus 帧（串口工具 / 脚本）即可擦掉 boot 自己
- 一旦 boot 被擦，设备**永久变砖**，只能返修

#### 方案

**boot 在协议层强制拦截**，对所有写操作做地址范围检查：

```
合法写入范围（白名单）：
    [APP_START, APP_END)  = [0x08010000, 0x080E0000)
    DAP_START..APP_END    = [0x080E0000, 0x08100000)   ← 是否允许写入需决策，见下

拒绝：
    任何与 [0x08000000, 0x08010000)（Boot 区）有交集的擦除/下载请求
```

##### 待决策点

- **Boot 区必须无条件拒绝**（这条没有商量余地）
- **DAP 区 `0x080E0000` 是否允许上位机写入**：如果未来要用这个 IAP 通道更新 DAP 固件，则允许但必须显式开关；否则一并拒绝

##### 建议的异常码

| 码 | 含义 |
|---|---|
| `0x20` | 目标地址越界（不在允许的写入区间内） |

##### 边界情形

请求区间**跨越**白名单边界时（例如从 `0x0800F000` 跨到 `0x08011000`），应**整包拒绝**并回 `0x20`。
建议判定用"区间相交"而非"起点落在区间内"，避免跨界绕过。

### G3 — 掉电保护（写入有效性标志）【P1】

#### 问题

擦除/下载过程中掉电是常态。当前没有任何持久化标记，重启后 boot **无法区分**：

- App 区本来就是空的（从未刷过）
- App 区写了 20KB 后掉电（半截坏镜像）

两种情况在 boot 眼里**完全一样**，都会执行 LEAVE 跳转 → 跳进半截固件 → 跑飞或 HardFault。

#### 方案：App 区末尾的有效性标志

利用 DAP 区起始的若干字节（或 App 区最后一个扇区的末尾，**需与固件布局协商**）存放标志：

```
写入流程：
    1. FC103 ERASE   → 擦除目标扇区
    2. 写 标志 = INVALID（0xDEADBEEF）
    3. FC101 DOWNLOAD → 写入镜像（含 G1 的 CRC32 尾块）
    4. 写 标志 = VALID（签名值，如 0x4F54494D）
    5. FC103 LEAVE    → boot 检查标志
        标志 != VALID → 拒绝跳转，留在 boot
        标志 == VALID → 正常跳转
```

**关键**：标志必须在**擦除之前**置 INVALID，这样任何中途掉电都留下 INVALID 标志。

##### 待决策

- 标志存放位置：建议 **DAP 区头部**（`0x080E0000`），避免占用 App 区尾部空间影响固件容量
- 标志位宽度：建议 32 位足够；若需多版本管理可用 64 位
- 标志是否需要防"回滚"（降级到旧固件）：本期不做，见 §5

### G4 — 协议版本协商【P1】

#### 问题

`FC104` 当前只返回 `[4B version BE][12B MCU UID BE]`，其中 `version` 是 **boot 固件版本**。上位机无法据此得知：

- boot 是否支持 CRC32 校验（G1）
- 镜像格式该怎么生成
- 未来新增能力的协商

#### 方案

**保持 FC104 响应长度不变**，把已有的 4 字节版本号重新定义为：

```
[0..1]  version_major : uint16 BE   boot 固件版本（沿用现有语义，例：V1.02）
[2..3]  caps          : uint16 BE   能力位图（见下）
[4..15] MCU UID       : 12B（不变）
```

**能力位图** `caps`（bit 从 0 起）：

| bit | 含义 | 建议初值 |
|---|---|---|
| 0 | 支持镜像 CRC32 自校验（G1） | 0（未实现时置 0） |
| 1 | 强制写入范围保护（G2） | 1（**应始终置 1**） |
| 2 | 支持写入有效性标志（G3） | 0 |
| 3 | 支持 DAP 区写入 | 0 |
| 4~15 | 预留 | 0 |

上位机侧读 `caps` 后决定是否生成 CRC32 尾块 —— **上位机逻辑必须以 `caps` 为准，不做版本号猜测**。

**为什么不改长度**：保持 FC104 响应长度不变 = 老版上位机读到新版 boot 不会解析出错，向后兼容成本最低。

## 4. 实现优先级与工作量

| ID | 改动项 | 优先级 | 固件工作量 | 是否需上位机配合 |
|---|---|---|---|---|
| G1 | 镜像 CRC32 自校验 | **P0** | 中（CRC 实现 + LEAVE 前校验流程） | 是（新工具链生成尾块） |
| G2 | 写入范围保护 | **P0** | 小（FC101/FC103 加范围判断） | 否 |
| G4 | 能力位协商 | **P1** | 小（FC104 返回值重定义） | 是（上位机按 caps 生成镜像） |
| G3 | 掉电有效性标志 | **P1** | 中（标志位管理 + LEAVE 检查） | 否 |

**建议落地顺序**：G2 → G4 → G1 → G3。
G2、G4 工作量小、收益直接，先行合入；G1 涉及镜像格式变更，需与上位机工具链同步，最后做。

---

## 5. 明确**不做**的事

为避免范围蔓延，以下本期不做：

| 项 | 理由 |
|---|---|
| 固件签名 / 公钥验签 | 安全启动（Secure Boot）是独立课题，本产品无防抄板诉求 |
| 镜像版本回滚保护 | 需要持久化版本存储与策略，本期无诉求 |
| A/B 分区 + 回滚 | 成本高（需双份 App 区空间），当前 832KB 够用 |
| boot 区写保护（option bytes） | STM32F4 无硬件 RDP 级别的 boot 保护，G2 的软件拦截已足够 |

## 6. 上位机侧的配套改动（G1/G4 需要）

以下**不是本文档要求固件实现的内容**，仅作记录，说明上位机将如何配合：

| 配套项 | 说明 |
|---|---|
| 按 `caps` 决定是否生成尾块 | 上位机读 FC104 的 `caps`，bit0=1 时在 .bin 末尾追加 12B 尾块 |
| CRC32 计算 | Python `zlib.crc32`（与固件算法口径一致） |
| hex 输出路径需相应处理 | 若用户直接导入 .hex，需先合并为连续二进制再计算 CRC |
| 校验失败提示 | 上位机可读取 boot 返回的异常码（`0x10`/`0x11`/`0x12`）给出更精确的错误文案 |

## 7. 待固件侧确认的问题

1. **DAP 区 `0x080E0000` 是否允许 IAP 写入？** 影响 G2 的白名单定义。
2. **有效性标志放在 DAP 区还是 App 区尾部？** 影响 G3 的实现与固件容量。
3. **`caps` 位图分配是否符合预期？** 是否需要预留更多位给后续特性（如 M3 的透传/采样）。
4. **镜像尾块是否需要预留扩展位？** 例如后续加 SHA-256，是否直接把 `MAGIC` 升级为版本号更灵活。
5. **LEAVE 时的 CRC 全量读回耗时可接受吗？** 832KB 按 248B/帧约 3400 帧；若担心耗时，可考虑只在 CRC 不匹配时才做二次确认，或由上位机在下载完成后主动请求校验（新增 FC）。

## 8. 变更影响面

| 侧 | 影响 |
|---|---|
| **boot 固件** | G1~G4 全部 |
| **app 固件** | **无影响**（仅 app 的 CMD_INFO_SER_NUM / capabilities 属计划 §6 的可选增强，与本文档无关） |
| **上位机** | G1/G4 需配套（见 §6）；G2/G3 无需改动 |
| **协议兼容性** | FC104 长度不变；FC101/FC103 仅**新增拒绝分支**，正常请求行为不变 |

## 9. 验收标准（建议）

| # | 场景 | 期望结果 |
|---|---|---|
| 1 | 正常镜像，CRC 正确 | LEAVE 成功跳转，app 正常启动 |
| 2 | 镜像被篡改 1 字节 | LEAVE 拒绝，返回 `0x12`，设备留在 boot |
| 3 | 镜像无尾块（LEGACY 格式） | 跳过校验，正常跳转（向后兼容） |
| 4 | 请求擦除 `0x08000000` | 拒绝，返回 `0x20` |
| 5 | 请求擦除跨越 boot/app 边界的区间 | 拒绝，返回 `0x20` |
| 6 | 下载过程中拔电 | 重启后标志为 INVALID，LEAVE 拒绝 |
| 7 | 老版上位机 ↔ 新版 boot | 正常通信，FC104 解析不报错 |
